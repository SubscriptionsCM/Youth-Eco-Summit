# Youth Eco Summit implementation plan

**Goal:** Implement the nonvisual platform in the supplied handoff, with closed-by-default configuration where programme decisions or services are unavailable.
**Architecture:** Next.js App Router, PostgreSQL transactional services, private S3-compatible storage adapter, durable PostgreSQL job queue. Plain responsive semantic UI; presentation is replaceable.
**Spec:** `Youth Eco Summit Developer Handoff.md`.

## Constraints and rulings
- No approved forms, providers, dates, judging policies or consent wording have been supplied. Build configuration and adapters; never invent live competition rules. No delivery deadline promise.
- The user explicitly authorizes implementation; no additional design approval gate. Visual design deferred.
- Fresh directory, no Git repository or existing app; work in the requested directory. No commits or worktree possible without initializing unrelated metadata.
- Provider-independent SQL query interface; real PostgreSQL migration also exercised using PGlite in tests. Production requires PostgreSQL.
- Submitted source code is never executed by the application. Storage reads are always authorized; signed URLs are used only for uploading parts.
- Separate participant identity, per-edition participation, entries, immutable revisions, assets, assignments and reviews.

## Tasks
- [x] Foundation: package, database migration, contracts and fixtures. Verify migration, uniqueness, foreign keys.
- [x] Auth module: contact OTP, sessions, invitation accounts, MFA, deactivation, CSRF, rate limits. Test expiry, replay, resend and authorization.
- [x] Storage module: multipart uploads, integrity/scan jobs, media gateway with ranges. Test incomplete/unsafe uploads and authorization.
- [x] Registration/submissions: school nominations/approval, returning schools, siblings, edition snapshots, versioned rules, drafts, final review and idempotent submit. Test limits and absent schools/files.
- [x] Judging: explicit and rule assignments, routing reconciliation, rubric validation, stale-save rejection, jury decision evidence. Test isolation and revocation.
- [x] Administration: pagination, search/filter, counts, exports, corrections, Trash preview/restore, retryable purge, import reconciliation and consent-gated publishing.
- [x] Functional UI: public content and configuration gates, forms, participant dashboard, admin and judge workspaces. Basic responsive/accessibility rules only.
- [x] Delivery: environment inventory, setup, operations/restore/cost/runbooks, requirement matrix; typecheck, tests, build and browser checks. See `docs/verification.md` for local results and the separate staging gates.

## Shared interfaces
`src/server/db.ts`: `Db.query<T>(text:string, params?:unknown[]):Promise<{rows:T[]}>`, `Db.transaction<T>(fn:(db:Db)=>Promise<T>):Promise<T>`, singleton `db`.
`src/server/core.ts`: `Actor {id:string, role:'owner'|'admin'|'judge'|'participant', contact?:string}`, `AppError(status:number,message:string)`, `requireAdmin(actor)`, `audit(db,actor,action,entityType,entityId,detail)`.
`src/server/access.ts`: `entryAccess(db,actor,entryId,write?:boolean)` returning joined submission row; admin can inspect Trash, participants and judges cannot. Judge checks active assignment, round, user, current revision and parents. `assetAccess(db,actor,assetId)` returns asset + entry after same check; gateway denies Trash for everyone.
`src/server/auth.ts`: `getActor(request:Request):Promise<Actor|null>`, `authAction(request:Request,path:string[]):Promise<Response|null>`. Own auth migration `002_auth.sql`.
`src/server/storage.ts`: `storageAction(request:Request,actor:Actor,path:string[]):Promise<Response|null>`, `verifyAsset(db:Db,assetId:string):Promise<void>`, `purgeObjects(keys:string[]):Promise<void>`. Own asset migration `003_storage.sql`.
API: catch-all `/api/[...path]`, JSON response `{data:...}` or `{error:string,fields?:...}`, no-store. Auth `auth/*`; storage `uploads/*`, `media/:id`; all remaining routes via domain router.
UI client calls central API. Domain contracts published separately before UI work starts.

## Verification
Test-first domain/permission cases; SQL integration tests run migrations against isolated PGlite; adapter tests use controlled external boundaries. Run `npm test`, `npm run typecheck`, `npm run build`; browser smoke tests for responsive public flows and errors. Provider round trips and representative backup/large-video/load tests remain staging gates until services and approved rules exist.
